## 질문·범위

고정 A/B 공개 상태에서 Qwen3.5-0.8B-Base(LoRA)를 행렬 탐색 자기대국으로 학습한다.

- 묻는 것: 탐색 없는 정책이 초기 P0보다 개선되는가, 그리고 개선이 언제 둔화되는가.
- 주장하지 않는 것: 일반 비공개 Gen9 OU, Qwen3.5-4B, L1-L5 효능, EX-079 대비 우월성.
- 학습 seed는 하나다.

## 모델·입력

- **base:** `Qwen/Qwen3.5-0.8B-Base` revision `dc7cdfe2ee4154fa7e30f5b51ca41bfa40174e68`.
  - 텍스트 backbone만 사용한다(vision·MTP 무시). bf16으로 동결한다.
- **LoRA:** r16, α32, dropout 0, FP32.
  - 대상: q/k/v/o/gate/up/down, DeltaNet in_proj_qkv/z/a/b, out_proj.
- **정책 head:** FP32 pointer head. decide 마커와 후보 닫기 토큰의 hidden을 scaled dot으로 비교하며, 양측이 공유한다.
  - key 사영을 0으로 초기화한다. 따라서 **P0 정책은 정확한 균등 분포**다.
- **가치 head:** FP32. VALUE 마커 hidden → Linear-Tanh-Linear-tanh 구조이며, 마지막 층을 0으로 초기화한다(P0 가치 ≡0).
  - 출력은 p1 관점이고 p2는 −v다.
- **입력 형식 `fixed-matchup-qwen-text-v1`** (chat template·절단 없음, 2,048토큰 초과 시 중단):
  1. 정적 부분: 형식 + 양 팀 원 세트
  2. `<|fim_middle|>` + 동적 상태
  3. `<|fim_suffix|>` (VALUE 마커)
  4. 루트·학습 행만: p1 후보 `<|box_start|>…<|box_end|>`, `<|quad_start|>`, p2 후보, `<|quad_end|>`
- 정적 접두 id는 진영 배정 2종을 prepare 때 동결한다.
  - 각 snapshot은 정적 접두를 1회 계산한다. 탐색 평가는 동결 base와 LoRA로 그 캐시를 재사용한다.
  - 학습은 공유 접두를 gradient 포함으로 다시 계산한다.

## 탐색

- **행렬 구성:** 결정마다 양측 합법 행동의 모든 조합을 만든다. 한쪽만 고르는 결정은 1×K다.
  - chance 표본은 조합당 1개이며 seed는 `[decision, a1_id, a2_id]`로 정한다.
  - 자식은 가치만 평가한다. 종료 자식은 ±1/0이다. 이렇게 보수 행렬 M(p1 관점)을 만든다.
- **풀이:** 루트 사전 정책 ρ를 magnet으로 둔 정규화 균형을 float64 log-space 동시 MMD로 푼다.
  - τ=0.2, η=τ/max(L,1e-3)², 최대 3,000회, duality gap ≤1e-6.
  - 한쪽만 고르는 결정은 closed form으로 푼다.
- **기록·사용:**
  - 정책 타깃은 π다.
  - 자기대국 행동은 π에서 T=1로 표본한다. 별도 ε은 없다.
  - 결정 기록에 ρ·M·π·q·자식 가치를 저장한다.
  - 선택지가 1개뿐인 쪽은 탐색하지 않는다.

## 학습

- **라운드:** 자기대국 32경기 = 16 seed블록 × 진영 배정 2(A=p1, B=p1).
  - 양측은 같은 snapshot을 쓰고, 결정당 탐색 1회를 양측이 공유한다.
- **replay:** 최근 8라운드.
- **step:** 라운드마다 128 optimizer step을 수행한다.
  - 배치 32행을 replay에서 균등 비복원 표본으로 뽑는다.
  - 표본이 소진되면 새 순열로 넘어간다.
- **손실:** CE(p1 후보, π1) + CE(p2 후보, π2) + MSE(v, z).
  - CE는 후보가 2개 이상인 쪽에만 건다.
  - z는 정상 종료 경기의 p1 관점 +1/0/−1이다.
  - 300턴 검열 경기는 가치 손실에서 빼고, 정책 손실에는 쓴다.
  - 기술 실패 경기는 학습에서 빼고 기록한다.
- **최적화:**
  - AdamW: LoRA lr 5e-5, head lr 5e-4, weight decay 0.01, 전역 grad clip 1.0.
  - 처음 50 step은 선형 warmup, 그 뒤 고정.
  - bf16 autocast, 결정론 설정.

## 평가·종료·선택

- **dev 평가:** 4라운드마다 수행한다. 탐색 없이 T=1로 두며, 매번 같은 dev seed를 쓴다.
  - 현재 모델 대 직전 평가 checkpoint 128경기 = 32블록 × 진영 배정 2 × 모델-팀 배정 2. round4는 P0와 비교한다.
  - 현재 모델 대 P0 64경기는 보고용이다.
- **점수:** 승 1, 무 0.5, 패 0. 300턴 검열은 0.5로 치고 따로 집계한다.
  - 평가 묶음에 기술 실패가 있으면 판정하지 않고 기술 중단한다.
- **둔화 종료:** 평가 점수 <0.55가 3회 연속(round4·8 포함)이면, round≥12 평가 시점에 종료한다.
  - **상한:** 100라운드. 시간 상한은 없다.
  - 종료 뒤에는 학습·평가를 더 하지 않는다.
- **선택:** 마지막 평가 checkpoint 최대 4개로 round-robin을 돌린다(쌍당 64경기, 탐색 없음).
  - Bradley–Terry(무승부는 반승) 최고 점수를 고르고, 동률이면 앞 checkpoint를 고른다.

## D-128 변경 (실행 전)

[D-128](../decisions/D-128-qwen-fixed-shape-serving.md)에 따라 다음 조항을 바꾼다. 개발 리허설5에서 G3·G4가 bf16 shape·경로 의존 반올림
(hidden 상대 L2 약 2%)으로 실패해 실제 실행 전에 멈췄다. 리허설 원자료는 `.pokechamp-data/dev/ex080-rehearsal-*`와
[EP-132 증거](../../../exec-plans/evidence/ep132/rehearsal)에 보존한다.

- **서빙:** 고정 shape만 쓴다.
  - 모든 추론 패스는 정확히 32행이다. 부족분은 그 패스 첫 행의 복사본으로 채우고 결과는 버린다.
  - 행은 자기 길이로 정해지는 버킷 128·192·256·320·384·448·512·640·768·896토큰까지 오른쪽 패딩한다. 896토큰을 넘으면 중단한다.
  - 가치 head도 항상 32행으로 계산한다. 따라서 행의 출력은 배치 구성과 무관하게 비트 동일하다.
- **처리량 측정:** 패스당 32행 고정. worker {16, 32} × search Node {1, 2}만 측정해 선택한다.
- **G3:** 홀로 평가한 결과와 섞어 평가한 결과가 hidden·가치·정책 모두 비트 동일해야 한다.
- **G4:** 캐시 경로·캐시 없는 참조 행·branch_hidden·루트 VALUE 대 가치 전용 행을 같은 GPU의 fp32 사본으로 비교한다.
  - 측정 정정(리허설6): fla Triton 커널은 fp32 입력의 dot를 TF32처럼 반올림한다. 그래서 fp32 사본에서는 Gated DeltaNet 규칙과
    짧은 합성곱만 transformers의 PyTorch 참조 구현(TF32 없음)으로 계산한다. 허용오차는 바꾸지 않는다.
  - 기준은 기존 허용오차(5e-3, hidden 1e-2)이다.
  - bf16 서빙 경로와 학습 경로의 반올림 차이는 기록만 한다.
- **확정한 구현 사항:**
  - fla Triton autotune은 시간 대신 설정 순서로 선택한다.
  - 서빙 LoRA는 bf16으로 둔다(출력 비트 동일).
  - PP는 슬롯 순서 위치 표기(`pp 31/7/-/-`)로 렌더링한다.
- 나머지 조건(G0·G1·G2·G5·G6·G7·G8 포함)은 그대로 둔다.

## 시도 1 중단과 도구 결함 복구 (2026-10-08, 학습 전)

[RD §11.1](../../../RESEARCH_DESIGN.md#defect-recovery)과 위 실패·복구 절을 따른다. 결함 기록과 원자료는
[증거](../../../exec-plans/evidence/ep132/defect-001-stale-response)에 있다.

- **발견:** 시도 1(identity `e51bfac1b3eae5a4673f16543c1c28d28e4811f6a07a844421fd1bb83ae758b3`)의 benchmark 단계.
  - GPU 게이트 G0~G8은 통과했다.
  - w16-n1 측정 뒤 w16-n2가 무효 900·정상 0을 내 컨트롤러가 멈췄다.
  - 학습·dev·test 자료는 없고, 결과를 보기 전이다.
- **원인:** 워커 응답 큐는 서버 기동 때 한 번 만들고 모든 Pool이 함께 쓴다.
  - benchmark Pool은 마감 시각에 끝나며, 이때 추론을 기다리던 경기를 취소한다. 서버는 그 요청에도 응답을 보낸다.
  - 다음 Pool에서 같은 번호의 워커가 그 응답을 읽고 'inference response identity changed'로 경기를 무효 처리했다.
  - 그 뒤로는 경기마다 앞 요청의 응답을 읽는 한 칸 밀림이 이어졌다.
  - smoke·라운드·dev는 Pool을 닫기 전에 모든 경기를 끝내므로 영향이 없다.
  - 리허설은 benchmark를 거치지 않아 이 경로를 실행하지 않았다.
- **영향 범위:**
  - 시도 1 w16-n2 측정은 무효다.
  - w16-n1은 깨끗한 채널에서 측정했지만, 네 조합을 한 identity에서 비교하도록 시도 2에서 다시 측정한다.
  - 실험 조건·게이트 기준·선택 규칙은 바뀌지 않는다.
- **수정:** 요청 식별자를 (Pool epoch, 순번)으로 바꿨다.
  - 다른 epoch의 응답이나 같은 epoch의 지난 순번 응답은 버리고, 경기별 `metrics.stale_responses`로 센다.
  - 그 밖의 불일치는 기존처럼 fail-closed다.
  - 변경은 `pool.py`와 기본 실행 경로(`config.py`)뿐이다.
- **검증:** 가짜 CPU 서버(정확한 P0 출력)와 응답 큐를 공유하는 실제 Pool 두 개로 재현했다.
  - 수정 전: 두 번째 Pool이 131/131 무효였다.
  - 수정 후: 두 번째 Pool이 24/24 정상이었고, 이전 응답 3건(Node 1)과 2건(Node 2)을 버렸다.
  - CPU 테스트 25개가 통과했다(새 단위 검사 포함).
- **복구 단위:** 학습 전이므로 시도 전체를 새 identity로 다시 시작한다(prepare → 게이트 → benchmark 네 조합 → smoke → 학습).
  - 이것은 경기 단위 자동 재수집이 아니라 도구 결함 복구다.
  - 시도 1 디렉터리(386MB)와 기록은 보존한다.
  - 시간 상한은 null이다. 디스크·GPU 사용량은 시도 1을 합산해 보고한다(시도 1: GPU2·3 각 약 26분).

## 시도 2 중단과 두 번째 도구 결함 (2026-10-08, 학습 전)

결함 기록과 원자료는 [증거](../../../exec-plans/evidence/ep132/defect-002-teardown-kill)에 있다.

- **발견:** 시도 2(identity `438727a6c172d0ad2820819fe4b30d128a3aead3c45cbfd70dd92347d235fb69`).
  - 게이트는 통과했다(기록이 시도 1과 비트 동일).
  - benchmark는 네 조합 모두 무효 0이었다. 측정 창마다 두 GPU가 99% 바빴고, 결정/초 최대 규칙으로 w16-n2를 골랐다.
  - 마지막 측정 Pool(w32-n2) 다음의 smoke가 실패했다: 정상 3/8, 무효 5/8. 무효 5건은 모두 첫 요청에서 900초 응답 timeout이 났다.
- **관찰:**
  - GPU2 서버의 메인 스레드가 커널 `pipe_read`에서 멈춰 있었다. 서버는 poll로 데이터가 있음을 확인한 뒤에만 읽으므로, 부분 메시지의 나머지를 기다리는 상태다. GPU3 서버는 정상이었다.
  - 컨트롤러는 시간 제한 없는 stop 호출에서 멈췄다. 서버 두 개를 수동 SIGTERM으로 끝내 GPU를 반환했다.
- **원인:** Pool 정리는 워커를 10초 기다린 뒤 SIGTERM으로 죽였다.
  - 추론을 기다리다 취소된 워커는 feeder 스레드를 비워야 끝날 수 있다. 그런데 정리 중에는 결과 큐를 읽지 않았고, 요청 메시지(약 60~100KB)는 64KB 파이프보다 커서 서버가 읽는 만큼 나뉘어 쓰인다.
  - 요청 큐의 쓰기 잠금을 쥔 채 메시지 중간에서 죽은 워커가 부분 메시지를 남겼고, 이를 읽은 GPU2 서버가 영구 대기했다.
  - 시도 1 결함과 계기(마감으로 끊는 benchmark Pool)가 같다. 첫 수정은 남은 응답만 다뤘고, 그 재현 검사(빠른 가짜 서버)에서는 워커가 10초 안에 끝나서 이 결함이 드러나지 않았다.
- **영향 범위:**
  - 시도 2 benchmark 측정은 서버가 정상인 동안 이뤄졌으므로 유효하다. 그래도 한 identity 비교를 위해 시도 3에서 다시 측정한다.
  - 시도 2 smoke는 무효이며 보존한다. 학습·dev·test 자료는 없다.
- **수정:**
  - Pool 정리를 협조적 종료로 바꿨다: 취소 신호를 보내고, 결과를 비워(폐기) 가며 최대 300초 동안 워커가 스스로 끝나기를 기다린다. 그동안 서버는 요청을 계속 읽는다.
  - 유예 뒤에도 남은 워커만 죽이고, 이 경우 공유 큐를 신뢰할 수 없으므로 예외로 단계를 멈춘다.
  - 서버 stop 호출에 120초 응답 제한을 두었다.
- **검증:** 가짜 CPU 서버가 공유 요청 큐를 느리게 읽게 하고 워커 32개 Pool을 마감으로 끊는 재현을 썼다.
  - 수정 전: 워커 32개가 모두 SIGTERM으로 죽었고, 서버가 `pipe_read`에서 멈췄으며, 다음 Pool의 요청 처리는 0건이었다.
  - 수정 후: 강제 종료 0, 서버 정상 대기, 다음 Pool 40/40 정상.
  - 서버가 읽지 않는 경우에는 유예 뒤 강제 종료하고 예외를 냈다(fail-closed).
  - 시도 1 재현 검사 회귀(24/24 정상, 지난 응답 2건 폐기)와 CPU 테스트 25개도 통과했다.
  - 최종 단계 집계(test·dev·round-robin·종료 규칙)를 일정 형태의 합성 결과로 확인했다.
- **복구 단위:** 시도 3을 새 identity로 처음부터 실행한다. 시도 1·2 디렉터리와 기록은 보존한다.
  - 누적 사용량: 시도 2는 GPU2·3 각 약 59분, 디스크 387MB다.
